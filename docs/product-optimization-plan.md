# 产品优化计划

更新时间：2026-06-25

## 目标

下一轮优化不以通用 agent / CLI 控制为主线，改为优先解决用户在真实剪藏中的两个高频问题：

1. 用户不想总是保存全文，而是想保存网页中的高价值摘录、观点、数据、案例或金句。
2. 用户想用飞书资料库，但首次配置表格、字段和模板的成本偏高。

本计划替代尚未进入开发的通用 agent / CLI 剪藏桥设想。agent 能力可以作为后续底层能力，但不作为本轮用户可见主功能。

## 全局约束

- 继续保持插件“网页知识剪藏与整理”的单一产品目的。
- 不新增业务后端，不做静默网页抓取，不做行为追踪。
- 不自动采集或上传网页 URL、标题、正文、标签、备注、飞书数据或用户身份信息。
- 所有保存、AI 整理、飞书建表或字段修改，都必须由用户主动点击触发。
- 分享模板、AI 提示词和预设表结构不得包含 App ID、App Secret、Notion Token、AI API Key、飞书 App Token、Table ID 或用户网页内容。
- 优先复用现有页面提取、Markdown 生成、飞书保存、模板、最近保存和侧栏 UI 模块。

## 1. 高质量摘录

### 用户价值

用户经常只想保存网页中的一段观点、一个数据、一句金句、一个案例或一段可引用素材。相比全文剪藏，摘录更容易回顾、写作和复用。

### 实施范围

- 支持从当前选中文本创建摘录，主路径放在网页阅读现场，而不是要求用户切到侧栏后再捕捉 selection。
- 增加右键菜单“保存选中内容为摘录”，允许用户直接保存到指定飞书资料库，或保存为 Markdown 摘录。
- 侧栏保留为整理、回顾和兜底入口，不再把“捕捉选中文本”作为主要操作。
- 摘录保存时保留：
  - 原网页标题；
  - 原网页链接；
  - 摘录正文；
  - 保存时间；
  - 摘录类型；
  - 用户备注；
  - 标签和下次回顾时间。
- 摘录类型首批支持：
  - 观点；
  - 案例；
  - 数据；
  - 金句；
  - 问题；
  - 其他。
- AI 整理仅作为用户主动触发的辅助能力，用于建议摘录类型、标签和一句话价值说明。
- Markdown 保存时明确区分“摘录”和“整篇网页”。
- 保存到飞书时优先复用现有字段映射；如用户资料库没有摘录字段，提供清晰提示，而不是静默丢弃。
- 最近保存与待回顾中心显示摘录标识，并允许打开原网页和管理回顾日期。

### 组件化方案

- 右键菜单优先使用 Chrome `contextMenus` 事件提供的 `selectionText` 获取摘录正文，避免侧栏切换焦点导致网页 selection 丢失。
- 侧栏兜底路径继续复用 `extractCurrentPageSnapshot` 获取当前选中文本，不新增独立页面解析逻辑。
- 新增通用摘录数据类型和转换工具，供侧栏、弹窗和后续右键入口复用。
- 扩展现有 Markdown 生成和飞书字段映射能力，而不是新增保存通道。
- 摘录入口的表单控件应复用既有标签、备注、回顾日期和保存反馈模式。

### 验收标准

- 当前页面有选中文本时，用户可以通过网页右键菜单将选中文本保存为摘录。
- 右键菜单能列出用户配置的资料库，用户可明确选择保存目标。
- 当前页面无选中文本时，摘录入口给出可操作提示，不进入空保存。
- 摘录保存为 Markdown 时包含来源、摘录类型、正文、备注、标签和回顾日期。
- 摘录保存到飞书时不会覆盖全文剪藏字段，也不会丢失来源链接。
- AI 摘录建议必须由用户主动点击触发；未启用 AI 时仍可手动保存摘录。
- 最近保存中能区分摘录和整篇网页。
- 不新增后端、遥测或自动上传。

## 2. 开箱即用的飞书资料库配置

### 用户价值

用户愿意使用飞书资料库，但不一定愿意先理解 App Token、Table ID、字段类型、字段映射和模板。插件应该把“能保存第一条飞书记录”的路径变短。

### 实施范围

- 保留零配置 Markdown 作为第一入口，不把飞书配置变成使用前置条件。
- 设置页增加“快速创建飞书资料库”路径：
  - 用户确认后，引导或调用能力创建推荐多维表；
  - 创建阅读收件箱、研究资料库、内容素材库之一；
  - 自动写入推荐字段；
  - 自动保存为插件资料库配置草稿。
- 对已有飞书表格，提供“检查并补齐字段”能力：
  - 读取当前字段；
  - 对照所选模板列出缺失字段；
  - 用户确认后补齐缺失字段；
  - 不删除、不重命名用户已有字段。
- 保存失败时提供人话错误：
  - 凭证缺失；
  - 飞书权限不足；
  - 表格链接无法解析；
  - 字段缺失；
  - 字段类型不匹配。
- 帮助页同步解释两条路径：
  - 先保存 Markdown；
  - 需要团队协作时再快速创建或连接飞书资料库。

### 组件化方案

- 复用现有资料库模板定义，作为建表字段来源。
- 复用现有表格配置、字段映射和模板分享逻辑，避免生成一套只供向导使用的数据结构。
- 新增“配置向导”UI 组件，设置页只负责状态编排。
- 飞书建表、建字段和字段检查应集中在独立服务模块，便于后续替换为 lark-cli / Skill / OpenAPI 实现。

### 验收标准

- 新用户不配置飞书仍能保存 Markdown。
- 用户可以从设置页选择一个推荐模板，创建或连接一个可用的飞书资料库。
- 已有表格不会被自动破坏；补齐字段必须二次确认。
- 创建和补齐字段后，插件能得到可保存的资料库配置。
- 所有飞书写入动作都有用户明确点击，不后台自动执行。
- 错误信息能说明下一步怎么修，而不是只展示 API 原始报错。
- 不运行 npm 构建或测试；完成静态差异检查后提醒用户重新加载插件验证。

## 暂不进入本轮

- 通用浏览器自动化控制。
- 定时页面爬取或后台自动订阅。
- 自动读取用户所有飞书空间或批量扫描表格。
- 自动创建复杂仪表盘、Workflow 或团队权限角色。
- agent / CLI 直接控制插件完成完整浏览器操作。

## 后续可讨论：飞书 CLI / Skill 植入

飞书 CLI / Skill 适合成为“快速创建资料库”和“检查补齐字段”的实现后端之一，但不应把 lark-cli 直接塞进 Chrome 插件运行时。

推荐后续单独评估三种实现：

1. 插件直接调用飞书 OpenAPI：适合普通用户，安装成本最低。
2. 本地 agent / lark-cli 辅助建表：适合高级用户和内部工作流，能力强但需要本地环境。
3. 生成可执行的 Skill/CLI 指令包：适合让 agent 帮用户一次性创建标准资料库，再把结果回填插件配置。
